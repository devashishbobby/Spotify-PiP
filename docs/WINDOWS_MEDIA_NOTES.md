# Windows media implementation notes

Phase 2 is implemented. See [the validation report](PHASE_2_WINDOWS_TESTS.md) for live native evidence, test commands and the complete T01–T16 matrix.

`src-tauri/src/media_session` owns all WinRT work. One dedicated MTA worker serializes discovery, snapshots and playback commands. The main Tauri thread only manages the window/tray and enqueues typed media requests. The queue holds at most 32 requests and returns a normalized busy error on overflow. WinRT asynchronous media operations have cancellation checks and a four-second deadline.

Only `SpotifyAB.SpotifyMusic_zpdnekdrzrea0!Spotify`, observed in a real `GetSessions()` result on this machine, is accepted. `GetCurrentSession()` is never called. Browser/source substrings are not accepted. Multiple matching sessions prefer playing, then retained, then enumeration order. Conventional desktop identifiers remain unverified and fail closed.

Session/track context generations increase on selection replacement, meaningful metadata identity changes and service recreation. Every transport command refreshes/revalidates the source, generation and OS control flags. Seeking also rereads and clamps to current absolute tick bounds. Rejected/false operations return structured errors; accepted operations trigger an authoritative snapshot refresh. No optimistic playback or track mutations occur in React.

Manager/session callbacks only mark dirty bits and wake the worker. Registration tokens are retained and removed during replacement/shutdown. Events are coalesced; timeline-only events cannot force high-frequency hidden updates. Fallback refresh is about 1.5 seconds visible/active, 10 seconds hidden/active, and 5 seconds absent. Session disappearance clears metadata/artwork, shows disconnected briefly, then absent; manager failures clear state and trigger recreation. A visible-window refresh reconciles after hiding.

Timeline conversion uses 10,000 ticks per millisecond and the Windows 1601 epoch for `LastUpdatedTime`. Position is relative to `StartTime`, duration is `EndTime - StartTime`, and invalid durations/seek bounds are rejected. Native position is advanced only using a valid OS anchor while playing. Frontend display-only interpolation uses a monotonic clock, clamps to duration, and stops while hidden or paused. See Microsoft's [timeline properties](https://learn.microsoft.com/en-us/uwp/api/windows.media.control.globalsystemmediatransportcontrolssessiontimelineproperties) and [DateTime definition](https://learn.microsoft.com/en-us/uwp/api/windows.foundation.datetime).

Artwork uses WinRT stream/DataReader APIs, a 2 MiB compressed limit, decoder-inspected pixel bounds (4096 edge and 16 million pixels), JPEG/PNG signature and MIME validation, and a single-current-track cache. Replaced images are released. Artwork failures are nonfatal and no artwork is persisted or fetched externally.

The frontend subscribes before its initial snapshot, ignores stale revisions, disposes late subscriptions correctly under StrictMode, and exposes pending/error/retry state. Mock mode requires an explicit development flag; normal desktop mode and every production build use the live hook. Fake IPC in browser tests is a test adapter, not a production fallback.

Following user feedback, explicit seeks bypass the regular timeline-only event throttle. Command validation and confirmation exclude artwork. A bounded 20 ms reconciliation burst follows an accepted seek, for at most 1.5 seconds; confirmation failure is an error rather than fabricated progress. The IPC result includes the revisioned authoritative snapshot, applied before pending UI is cleared. A pending target is only a visible interaction preview and rolls back on failure. A native seek-plus-confirmation sample measured 62 ms.

The requested volume button uses `audio_volume.rs` and Windows Core Audio `ISimpleAudioVolume`. Each audio session must have an unambiguous single process, exact package family `SpotifyAB.SpotifyMusic_zpdnekdrzrea0`, and executable basename `Spotify.exe`. Missing, expired, shared-process or multiple matching sessions fail closed. All discovery, writes and COM releases stay on the media worker. Volume is cached for ordinary snapshots and freshly revalidated for writes; external changes reconcile on refresh. This is Windows per-app volume and mute, separate from Spotify's internal volume. No endpoint setters or global media-volume keys are used. Native write/mute/restore checks passed with three other application sessions and two endpoint master volumes unchanged. See [Microsoft's session-volume interface](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nn-audioclient-isimpleaudiovolume).

`RequestAsync()` succeeded in this unpackaged Win32 development environment without adding an invented UWP manifest capability. Future installer/other-machine access still requires validation. No OAuth, Web API, external artwork service, master-volume command, unrestricted shell/filesystem IPC or audio handling was introduced.

Phase 3 remains separate: persistent settings/position, instance policy, installer/autostart and packaging validation.
